## docs/gpu-utilization-plan.md 可行性评审（仅分析，未改代码）

- 结论：路线图方向正确、阶段 1 代码可信，但整份文档**没有任何真机基线数字**，
  阶段 2–5 的优先级是推断而非实测；阶段 1 真机验证前不应动后续阶段。
- 代码核对属实：`--workers`(cli.py:526)、Per-Thread 切换(headless.py:108-111)、
  2N 有序窗口(headless.py:606-626)、worker stream 绑定(VideoManager.py:310-319 /
  Models.py:894-939)、`run_swapper_batched`(Models.py:997)、Fraction(headless.py:518)、
  `elapsed`(cli.py:607)。
- **两处需修正的判断**：
  1. 阶段 2「编码独立线程 / 中–高收益」被高估——`_parallel_swap_frames` 的 2N
     窗口在阶段 1 已让编码与 GPU 推理重叠；窗口满时主线程本就阻塞在
     `f.result()`。且 PyAV/libx264 `encode()` 是否释放 GIL 未验证，存在负收益。
  2. 「已通过离线测试」含金量有限：`test_cli.py:145-154` 的
     `test_parallel_path_preserves_order` 是读 headless.py 源码查 `popleft()` /
     `f.result()` 字符串，不是行为测试，证明不了保序或 GPU 正确性。
- 额外隐患（文档未提）：`VideoManager.swap_video` 每个 worker 都往同一条默认
  stream 插 `wait_stream`(VideoManager.py:319)，而 `_swap_frame` 的 `.cpu().numpy()`
  (headless.py:630-631) 在默认 stream 上做 D2H，可能形成跨 worker 隐式屏障。
  另：2N 窗口的主机内存（4K + workers=8 约 750MB）文档只算了 VRAM。
- 测试实跑：6 个模块中 5 个通过；`test_target_match` 因本机未装 numpy 退出 1
  （本地 Windows 无 GPU 栈，非代码缺陷）。本机 numpy/torch/cv2/ort/av/PIL 全无。
- 建议顺序：先补阶段 0 的 `avg fps`（`report["frames"]` 在 cli.py:358 的
  `_cmd_video` 作用域内可用，改动很小）→ 跑 3.4 的 workers=1/2/4 真机矩阵 →
  再决定是否做阶段 2。

## 阶段 4 的 7.1 评估 → 冻结；改实现替代优化

- **判据成立但不足以支撑实现**：`swap_core` 的 paste_back 只读写
  `img[0:3, top:bottom, left:right]`（VideoManager.py 约 917–925）。
- **五条阻断条件**（已写入 gpu plan 7.1）：
  1. `run_swapper_batched` 的 N 是 polyphase phase 数（dim²），不是脸数；
     `swap_core` 里 dim 恒为 1 → n_phases=1 → batch 分支实际从未被调用。
     `_polyphase_pass_v1` 用的是「一张脸抽稀成 tile」，不是多脸。
  2. `pipeline_size` 按每张脸 scale 独立算，范围 128–swap_size，batch 需统一
     (N,3,128,128)。
  3. `swap_core` 是 438 行单体函数（499–927），batch 必须拆三段或复制
     ~65 行 paste-back，本地无法验证像素等价。
  4. **输入阶段已有数据依赖**：`pipeline_input_face` 从当前 img warp（571–579），
     逐脸路径后一张脸读到前一张已写回像素（925）；预批量准备读原始 img，
     bbox 重叠时结果不同。文档「按序回填」补不回读侧差异。

  `run_recognize` 的 embedding **没有任何读取方**（411–427 分支只用
