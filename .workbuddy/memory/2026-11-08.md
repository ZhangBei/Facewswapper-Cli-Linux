## 项目结构分析（只读，未改动代码）

- 本工作区是 headless Faceswapper CLI（Qt 桌面应用的后代），目标 Ubuntu 24.04 + NVIDIA GPU；本地 Windows 无 GPU / 无推理栈。
- 四层单向依赖：`cli.py` → `headless.py` → `VideoManager.py` / `Models.py`。核心 30 个模块约 9,100 行，`Models.py` 2,405 行、`VideoManager.py` 1,846 行最重。
- 三条关键约定（改动前必须知道）：
  1. `VideoManager.self.parameters` 是 54 个 key 的扁平 dict，保留 GUI 时代 `*TextSel` / `*Slider` / `*Switch` 命名，因为 `saved_parameters.json` 是磁盘契约（见 docs/adr/0001）。加功能要在 `parameters.py` + `_default_data.py` + `cli.py` 映射 + `model_store.specs_for_parameters` 同步登记。
  2. 所有 swap pass 共享 `(H,W,3)` float 0-1 输入输出契约；模型差异（emap 投影、[-1,1] 值域、polyphase tiling）封装在 pass 内部。
  3. `model_store.py` 与约 10 个策略判定模块刻意 stdlib-only，让下载与离线测试不依赖 GPU 栈；测试不用 pytest，`python -m faceswapper.tests` 子进程编排。
- `models/` 当前为空，3 个基础模型约 450 MB 由下载器按需拉取（huggingface / hf-mirror / github / 自定义 URL）。
- 性能结论（docs/gpu-utilization-plan.md，Tesla T4 真机）：11 个优化阶段全部收口，除 `--workers 2` 约 1.5× 外其余开关均无收益或不可用；7.1 / 7.2 batch 闸门保持 `False`，阻断点是像素等价性（PSNR 45.69 dB），不是模型能力。
- 本机实测 `python -m faceswapper.tests`：22 模块，21 PASS / 1 SKIP / 0 FAIL；唯一 SKIP 是 `test_target_match`（本机连 numpy 都未安装）。

## 结论：整体框架不重构

- 判断：四层单向依赖干净，真机已证伪「结构导致慢」（瓶颈是 cudaStreamSynchronize 75.6% + 逐脸 ORT 调用），换骨架收益为零、回归面全量；参数 dict 是磁盘契约不能动。**不动整体架构，只做局部有界收敛。**
- 量化：`Models.py` + `VideoManager.py` + `headless.py` = 5,381/9,085 行（59%）；8/22 个测试模块、1,360/5,142 行（26%）是读源码 regex/AST 的结构断言；4 个实验闸门保持 False；2 个未挂载 GPU 方法；`trt_dump_ep_context_model` 注释重复 4 处；加一个 swapper 需同步 9 处注册表。
- 核心约束：结构断言不是偷懒，是本地无 GPU / 无 numpy 的必然妥协；唯一可信的像素级验证是逐帧 PSNR=inf，只能在真机跑。缺可验证性时做结构性重构等于盲改。
- 重构触发条件：接第 3 个 swapper 模型（才值得把 9 处注册表改声明式）、7.1 真要解冻（才重构 prepare/finish）、需多机稳定部署（才补 pyproject / lock）。
- 建议试金石：`model_store.py`（779 行，stdlib-only，394 行行为测试）是唯一「够大且本机可 100% 验证」的模块，适合先拿它验证局部重构是否零回归。

## 多张 --target-face 侧脸参考图是否有效（结论）

- 参考图**不合并**：`_target_embeddings():508` 是 list comprehension，M 个独立 512-d 锚点（对比 `--source` 多张会走 `EmbeddingMerge.combine()`）。判定是 `any(...)` OR 语义，M 次独立配对判定，任一过线即换，因此召回↑、精确率↓。
- 实测阈值（base=55）：C=0 时恒 55.00；C=20 时「正脸帧+正脸参考」=55.00、「正脸帧+侧脸参考」=41.67、「侧脸帧+侧脸参考」=**35.00**。堆侧脸图 + 开补偿是双重放宽。`frontalness` 在左右眼翻转（eye_dist<=0）时返回 0.0 视为全侧。
- 假阳性放大（单张 p=0.10，1-(1-p)^M）：M=1 → 0.100，M=2 → 0.190，M=4 → 0.344，M=8 → 0.570。
- 算力几乎免费：每帧 GPU 推理仍是 N 次 ArcFace，不随 M 变；只多 O(N×M) 次 CPU 512 维点积，准备阶段多 M 次 detect+recognize（一次性）。代价全在误换。
- 根治在特征层/检出层：`--recognize-mirror`(×2) / `--recognize-dim2`(×4) / `--recognizer glintr100`(×4，需下载 arcface100) / `--align 68-point`；侧脸检不出时多参考图完全无效，需 `--detect-input-size 960` / `--detect-type SCRDF` / `--detect-retry`（`--detect-score` 有 unit bug，暂勿用）。
- 建议顺序：先 `inspect` 区分检不出 vs 匹配不上 → 单变量 A/B `--recognize-mirror --pose-compensation 15` → 确需堆图时只放同一个人 2~3 张不同偏航角，并把 `--target-threshold` 从 55 提到 60~65 抵消 any 放大；不要同时开大补偿 + 堆侧脸图。

## 现状：能否区分图片里正脸 / 侧脸

- 底层有 `frontal_match.frontalness(kps)`（stdlib-only，5 点 kps → 0-1），但**没有现成入口**。生产唯一调用链 `VideoManager.py:577 → effective_threshold_pair → frontalness`，而 `frontal_match.py:66` 的 `if compensation <= 0: return base_threshold` 使默认 C=0 时它一趟都不跑；只有 `--pose-compensation > 0` 且有 `--target-face` 时才计算。
- `cli._cmd_inspect():330-343` 只打印脸数与 `slot['Scale']`（眼距）；`headless._detect_face_slots():281` 里 kps 是局部变量、没存进 slot，连关键点都拿不到。
- 算法 `clip(1 - |nose_x - eye_mid_x| / eye_dist / 0.6, 0, 1)`；实测分档建议 ≥0.8 正脸 / 0.4~0.8 半侧 / ≤0.4 侧脸。局限：只看水平偏航 x 坐标，不看俯仰与平面内倾斜；`eye_dist<=0`（左右眼翻转）或退化输入直接返回 0.0，0 分不区分「全侧脸」与「坏 kps」；是线性代理分数不是角度；依赖 detector 5 点质量。
- 易混淆：`orientation.py` 是整帧 90/180/270 朝向；`VideoManager.py:523` 的 `tilt=arctan2(眼轴)` 是 OrientAutoSwitch 的整帧旋转微调 EMA；`--align 68-point` 只把 68 点折成 5 点供 ArcFace 对齐。三者都不做正/侧脸分类。
- 若要做成正式入口：给 `inspect` 加一列，约 2 文件 5 行（slot 存 kps 或 frontalness，`_cmd_inspect` 打印值与标签）；`frontalness` 已由 `test_frontal_match.py` 覆盖。
